# Восстановление PyTorch и дообучение распознавателя Indra

Экспериментальный код в `indra_ocr/finetune/` восстанавливает **распознаватель
строк `rec.onnx`**, проверяет численное совпадение с оригиналом, дообучает его
с CTC-loss и экспортирует обратно в формат Indra. Это добавленный локально код,
не официальный trainer Datalab. Детектор, порядок чтения, китайская и
математическая модели здесь не обучаются.

Локально проверено 17 октября 2026 года на CPU: восстановление 1 236 110
параметров, совпадение IDs и длин с ONNX, дообучение, расширение словаря,
продолжение с оптимизатором, экспорт и запуск через публичный OCR API.
30 тестов прошли; 1 существующий тест пропущен из-за отсутствия опционального
`pikepdf`. Точные версии зависимостей, хеши весов и метрики smoke-теста записаны
в [FINETUNING_VALIDATION.json](FINETUNING_VALIDATION.json).

## Что именно восстановлено

Для релиза моделей `v3.1.1`: вход `[B,1,32,W]`, свёртка `[128,1,32,4] с шагом
`[32,4]`, BatchNorm и HardSwish; 10 residual-блоков с depthwise Conv1d
`kernel=9`, расширением 128 → 256, masked squeeze-excitation 256 → 64 → 256,
проекцией 256 → 128; выход Conv1d на 1678 классов. Нулевой класс — CTC blank.
Длины последовательностей: `min(ceil(width/4), padded_width/4)`.

Маски после каждого блока и masked pooling в SE нужны для корректных батчей
строк разной ширины. Они восстановлены из ONNX, а не заменены приближением.

В ONNX часть BatchNorm уже объединена с depthwise-свёртками. Восстанавливается
эквивалентная **вычислительная модель для инференса с обучаемыми весами**, а не
точная исходная модель до экспорта. Исходные BN-статистики этих слоёв,
оптимизатор, расписание обучения и аугментации недоступны. Оставшийся stem
BatchNorm при дообучении использует фиксированные running statistics, его
affine-параметры обучаются.

`model.safetensors` содержит те же ONNX-initializer веса с префиксом `rec/`,
включая уже объединённые свёртки. Если файл есть в папке исходных моделей,
`recover` проверяет его полное совпадение с `rec.onnx` и загружает веса из него.
Если файла нет, веса извлекаются непосредственно из ONNX.

## Установка и восстановление

Из корня клонированного репозитория:

```bash
uv venv --python python3.13 .venv
uv pip install --python .venv/bin/python -e '.[train]'

.venv/bin/python -m indra_ocr.finetune download \
  --out .model-source --revision v3.1.1 --with-safetensors

.venv/bin/python -m indra_ocr.finetune recover \
  --source .model-source --out runs/recovered.pt
```

`recover` перед сохранением сравнивает **сырые logits**, argmax IDs,
вероятности и длины с ONNX Runtime: разные размеры батча, разная ширина строк,
дополнение справа, пустая белая строка, ширина до 4096 пикселей. При
расхождении завершится с ошибкой. В checkpoint сохраняются SHA256 исходных
файлов, архитектура, словарь и результат проверки.

Повторная проверка; `--manifest` добавляет проверку на ваших изображениях:

```bash
.venv/bin/python -m indra_ocr.finetune verify \
  --checkpoint runs/recovered.pt --onnx .model-source/rec.onnx \
  --manifest /absolute/path/to/data/valid.jsonl
```

Команда `verify` предназначена для восстановленного checkpoint **до обучения**.
После обучения веса закономерно отличаются от оригинала. При экспорте
проверяется уже совпадение обученной PyTorch-модели с её новым ONNX.

## Свои данные

JSONL в UTF-8, одна запись на строку. Пути изображений считаются относительно
manifest. Текст — точная транскрипция одной строки:

```json
{"image":"lines/0001.png","text":"Пример строки текста"}
{"image":"lines/0002.png","text":"Өфө ҡалаһы"}
```

Такие изображения должны быть обрезаны близко к чернильной области строки.
Если есть исходная страница и координаты чернильной области, лучше указать их
явно. Координаты задаются в пикселях оригинального изображения:

```json
{"image":"pages/page01.png","bbox":[120,240,970,276],"text":"Пример строки текста"}
```

Обработка совпадает с `rec_preproc.crop_line`: grayscale, поля 0.2 высоты
сверху/снизу и 0.3 по бокам, масштабирование к высоте 32 с сохранением пропорций
(ширина ограничена 4096), ink map от 0 до 1, дополнение справа до кратности 8.
Поэтому не добавляйте большие белые поля к уже обрезанным строкам. Данные с
целой страницей и её полной транскрипцией без строковой разметки не подходят.

Разделите train/valid **по исходным документам**, чтобы строки одной страницы
не попали в обе выборки. Trainer не создаёт искусственный validation split.
Ошибки в путях/изображениях, неизвестные символы, пустые тексты и невозможные
для CTC транскрипции вызывают явную ошибку. Повторяющиеся символы учитываются
при проверке минимального числа CTC-шагов.

## Дообучение

```bash
.venv/bin/python -m indra_ocr.finetune train \
  --checkpoint runs/recovered.pt \
  --train /absolute/path/to/data/train.jsonl \
  --valid /absolute/path/to/data/valid.jsonl \
  --out runs/my-data --epochs 10 --batch-size 8 --lr 0.0001 --device auto
```

`auto` выбирает CUDA, если она доступна, иначе CPU. MPS не используется из-за
CTC. Уменьшите batch size для длинных строк. CUDA поддержана кодом, но локальная
проверка выполнена на CPU. Trainer использует AdamW, gradient clipping,
фиксированный seed и проверяет конечность loss/градиентов.

В новой папке запуска появятся:

- `last.pt`: модель, metadata, оптимизатор, epoch, step, RNG и последние метрики;
- `best.pt`: checkpoint с минимальным validation CER;
- `metrics.jsonl`: train loss, validation loss и CER каждой эпохи;
- `arguments.json`: параметры запуска.

CER — сумма расстояний Левенштейна между нормализованными эталонами и greedy
CTC-результатами, делённая на число символов эталонов; значение может быть > 1.
Без `--valid` CER не измеряется и `best.pt` выбирается по train loss. Это не
оценка качества на новых документах.

Если встречаются новые символы, добавьте `--extend-vocab`: новые токены
дописываются в конец, старые IDs и строки классификатора сохраняются. Новые
строки классификатора инициализируются заново. Одной правки `meta.json`
недостаточно. В опубликованном словаре уже есть `ӘӨҮҠҒҘҪҢҺ` и строчные пары,
но наличие символов не гарантирует качество на башкирских документах.

Для продолжения с оптимизатором, сохранённым checkpoint и следующего номера
эпохи (папка результата должна быть новой):

```bash
.venv/bin/python -m indra_ocr.finetune train \
  --checkpoint runs/my-data/last.pt --resume \
  --train /absolute/path/to/data/train.jsonl \
  --valid /absolute/path/to/data/valid.jsonl \
  --out runs/my-data-continued --epochs 5
```

`--epochs` задаёт число **дополнительных** эпох. `--max-steps N` ограничивает
суммарное число шагов и удобен для smoke-теста. При остановке посреди эпохи
продолжение начинается со следующей эпохи, а не с точной позиции в manifest.
При `--resume` параметры оптимизатора восстанавливаются из checkpoint.

## Экспорт и использование

```bash
.venv/bin/python -m indra_ocr.finetune export \
  --checkpoint runs/my-data/best.pt --base-model-dir .model-source \
  --out runs/my-model --manifest /absolute/path/to/data/valid.jsonl

.venv/bin/python -m indra_ocr scan.png --model-dir runs/my-model
```

Экспорт создаёт `rec.onnx` с динамическими batch/width и выходами
`ids, conf, lengths`, проверяет его против PyTorch, переносит остальные модели
и обновляет `meta.json`. Исходная папка должна соответствовать версии, из
которой восстановлен checkpoint. `rec.int8.onnx` не переносится: Indra иначе
предпочтёт старые квантованные веса. Выходная папка должна быть новой.
`finetune.json` содержит provenance и результаты проверки экспорта.

Улучшение качества на ваших данных нужно измерять на отложенных документах:
само успешное восстановление и уменьшение training loss его не доказывают.
Веса остаются производными от опубликованных весов Datalab; их исходная
[лицензия](https://huggingface.co/datalab-to/indra-ocr/blob/main/LICENSE)
при копировании модельной папки сохраняется.
